# The synthetic sample data

Every notebook in this toolkit runs on the two files in this folder. They are
small enough to sit in the repository, so you can work through the entire book
before you go anywhere near national data.

| File | Records | Description |
|:--|--:|:--|
| `fonasa_sample.csv` | 30,000 | Extract of a synthetic health-insurance register |
| `suseso_sample.csv` | 27,000 | Extract of a synthetic social-security register |

**4,500 people appear in both files.** That is the ground truth, and it is the
reason this dataset is useful for learning: you can measure how many of those
4,500 your model finds, and how many of the pairs it proposes are wrong.

## These are not real records

The data is synthetic. It was generated by Nicolas Libuy in 2024 from frequency
tables supplied by the Instituto Nacional de Estadísticas (INE) of Chile, which
described how often each value of each identifying variable occurred in the
country's health-insurance (Fonasa) and social-security (Suseso) registers, and
how often those values were mistyped, abbreviated or missing.

Values were then drawn at random from those frequency distributions and
perturbed with the same error patterns. The result reproduces the *statistical
and error structure* of the real registers without containing any real person's
record. No individual in these files exists.

## Schema

Both files have the same columns.

| Column | Type | Description |
|:--|:--|:--|
| `unique_id` | string | Record identifier, `F0000001...` or `S0000001...`. Carries no information. |
| `nombre` | string | Given name(s), as held in the source system |
| `ap1` | string | First surname (paternal), as held in the source system |
| `ap2` | string | Second surname (maternal), as held in the source system |
| `sexo` | string | Sex, uncoded: `HOMBRE`, `MUJER`, or missing |
| `nacionalidad` | string | Nationality, uncoded: `CHILENA`, `EXTRANJERA`, or missing |
| `true_person_id` | string | **Ground truth.** Two records with the same value are the same person. |

The Spanish field names are kept because they are the names the source registers
actually use, and because seeing real register field names is closer to the
situation you will face than seeing tidied English equivalents. Chile's naming
convention gives each person two surnames, `ap1` from the father and `ap2` from
the mother; if your registers hold a single surname, read `ap1` throughout and
ignore `ap2`.

## The data is deliberately messy

These files are **raw**, exactly as they would arrive from a source system.
Names carry accents, typographical errors and inconsistent spacing; categories
are unstandardised; about 5% of values in each identifying field are missing.
Cleaning and standardising them is the first thing the toolkit does, in
chapter 2.2 (Data readiness), and it matters enough that skipping it changes
the linkage result.

## About `true_person_id`

You will not have this column. It exists here only because the data is
synthetic and we know who is who by construction. It is what makes it possible
to *measure* linkage quality in these examples rather than only assert it.

Treat it as a teaching aid, not as an input: never block on it, never include it
in a comparison, and never let it reach a model. The toolkit uses it in exactly
one place, evaluation, and says so each time.

When you move to your own data you will have no such column, and chapter 2.8
(Evaluation) covers what to do instead.

## Regenerating these files

The extract is drawn from the full synthetic registers, which total around
1.6 GB and are not distributed here. `scripts/build_sample_dataset.py`
documents and reproduces the sampling exactly, with a fixed seed:

```bash
python scripts/build_sample_dataset.py --source-dir /path/to/full/csvs
```

The sample is stratified: 4,500 person identifiers present in both registers,
plus fillers drawn only from identifiers present in neither, so the number of
true matches is exactly 4,500 and not one more.
